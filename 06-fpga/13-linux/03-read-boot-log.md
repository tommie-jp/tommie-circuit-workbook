# 13-3 起動の記録を読む — OpenSBI・カーネル・init・シェルの区切り

この題は実体配線図と Analog Discovery 3 とオシロの図を付けない。PC の中で動く組まない題で、13-2 の模型をそのまま使い、記録の読み方だけを足すから。

> [!NOTE]
> この題の数は、13-2 と同じ 1 回の起動 (soft-fpga-riscv-linux の fd1efd5、2026-11-11) の記録から取った。
> 実物の FPGA のボードでは動かしていない。

13-2 で Linux をシェルまで起こすと、約 350 行の記録が残る。この題では、その記録を読む。
記録には 3 つの時計が混ざっている。PC の実時間、模型のクロック数、カーネルが自分で数えている時刻である。
この 3 つを区切りごとに並べると、14 分のうちどこに時間がかかっているか、CPU がその間に働いているのか待っているのかが分かる。

この題では、

1. 記録の行の種類 (UART の字、`@@PC` などの模型の行、最後のまとめ) を見分ける
2. 行の頭に実時間を付け、区切りの表を作る
3. カーネルの時刻とクロック数の関係を確かめる
4. 1000 万クロックごとの「終えた命令の数」から、CPU が働いている区間と待っている区間を分ける

をする。

## 記録の行の種類

`make linux-sd < /dev/null` の出力には、3 種類の行がある。

| 行 | 例 | 出す物 |
| --- | --- | --- |
| UART の字 | `OpenSBI v1.9`、`[    2.727134] Run /sbin/init as init process` | CPU の上のソフト。UART のレジスタに書いた字を、模型が標準出力へ出す |
| 模型の行 | `@@PC 160000000 ffffffff805d34a8 retired 95550917` | 試験台 (`tb_mmrisc2.sv`)。`+pcmon=10000000` で、1000 万クロックごとに出る |
| まとめ | `334348446 cycles, 129116476 retired, 6156 traps, …` | 試験台と `main.cpp`。止まった時に 1 度出る |

模型の行は 3 行ひと組で出る。

```text
@@PC 170000000 ffffffff805d3ab0 retired 96620821
@@IRQ ext=0000 plic_irq=00 pend=0000 gw_ready=1111 claims u/t/eth/sd=0/0/0/38 mip=0000000000000000
@@SD card=0 cmd_done=1 data_done=1 ev_en=00001 rf=0 b2m 4096/4096 en=1 m2b 4096/4096 en=1 dma=0 uart_en=10
```

- `@@PC` は、クロック数・最後に終えた命令の番地・終えた命令の数。CPU の世界では、命令を最後まで実行し終えることを退役 (retire) と言う。
  パイプラインの CPU は命令を何段かに分けて同時に進め、途中で捨てる命令もあるので、「終えた」数で数える
- 番地が `ffffffff8…` で始まればカーネルの中、`000000000012…` のように小さければユーザーのプログラム (ここでは BusyBox) の中である。
  Sv39 の仮想番地は、上半分がカーネル、下半分がプロセスに割り当てられている
- `@@IRQ` の `claims u/t/eth/sd` は、割り込みコントローラ (PLIC) が受け付けた割り込みの数。順に UART・timer0・イーサネット・SD カード
- `@@SD` は SD カードの模型の状態。`b2m 4096/4096` は、カードから主記憶へ 4096 バイトのうち 4096 バイトを渡し終えた、の意味 (13-12 で使う)
- `@@` の行が、字の出ない長い区間で役に立つ。字が出なくても `retired` が増えていれば、CPU は止まっていない

## 行の頭に実時間を付ける

模型は実時間を記録しない。出力をパイプで受けて、行が来た時刻を頭に付ける。
道具は `sim/03-boot-milestones.py` (この題のために書いた。Python 3 だけで動く)。

```bash
make linux-sd < /dev/null 2>&1 | python3 03-boot-milestones.py --stamp > boot.log   # 行の頭に [実時間 秒] を付ける
python3 03-boot-milestones.py boot.log > 03-boot-milestones.csv                     # 区切りを抜く
```

```text
[   411.0] [    2.675088] EXT4-fs (mmcblk0p2): mounted filesystem … r/w with ordered data mode. Quota mode: disabled.
[   415.9] @@PC 160000000 ffffffff805d34a8 retired 95550917
[   417.4] [    2.727134] Run /sbin/init as init process
```

- 左の `[ 411.0]` が PC の実時間 (秒)、次の `[ 2.675088]` がカーネルの時刻 (秒)。`@@PC` の次の数がクロック数。これで 3 つの時計が 1 つの記録に並ぶ
- 区切りのクロック数は、前後の `@@PC` の行 (クロック数が分かっている) から、実時間で直線に補って出す。模型の速さはほぼ一定なので、ずれは数十万クロックに収まる
- 記録の全部 (351 行) はこの題に載せない。区切りを抜いた [03-boot-milestones.csv](03-boot-milestones.csv) と、
  `@@PC`・`@@IRQ` の行を表にした [03-boot-progress.csv](03-boot-progress.csv) を隣に置いた

## 区切りの表

| 区切り | 実時間 | カーネルの時刻 | クロック数 | 50 MHz のボードなら (計算値) |
| --- | --- | --- | --- | --- |
| 模型が走り始める | 0.8 秒 | — | 0 | 0 |
| OpenSBI の名乗り | 11.3 秒 | — | 約 400 万 | 0.08 秒 |
| カーネルの最初の行 | 24.6 秒 | 0.000000 秒 | 約 920 万 | 0.18 秒 |
| カーネルの時計が動き出す | 63.6 秒 | 0.000016 秒 | 約 2420 万 | 0.48 秒 |
| PLIC を見つける | 131.5 秒 | 0.519990 秒 | 約 5030 万 | 1.01 秒 |
| 本番のコンソールに替わる | 294.5 秒 | 1.756236 秒 | 約 1 億 1210 万 | 2.24 秒 |
| SD カードを見つける | 365.9 秒 | 2.317146 秒 | 約 1 億 4020 万 | 2.80 秒 |
| ext4 を mount | 411.0 秒 | 2.675088 秒 | 約 1 億 5800 万 | 3.16 秒 |
| init を起こす | 417.4 秒 | 2.727134 秒 | 約 1 億 6060 万 | 3.21 秒 |
| シェルの名乗り | 857.1 秒 | — | 約 3 億 3360 万 | 6.67 秒 |
| プロンプトで止まる | 859.0 秒 | — | 334 348 446 | 6.69 秒 |

- 実時間は `make` を打ってからの秒。最初の 0.8 秒は、模型のプロセスが 256 MB の主記憶を用意し、像を読む時間
- 14 分 18 秒は、大きく 2 つに割れる。カーネルが init を起こすまでが 6 分 57 秒 (1.6 億クロック)、init からシェルまでが 7 分 20 秒 (1.7 億クロック)
- OpenSBI が名乗るまでに約 400 万クロックかかる。字を出す前の初期化で、何をしているかは追っていない
- シェルの名乗りとプロンプトの間は、BusyBox が名乗りの字を 1 字ずつ UART へ出す時間と、止める前の 2 万クロック (13-2)

### カーネルの時刻はクロックを数えた物

カーネルの時刻と、補ったクロック数を、2 つの区切りの間で比べる。

| 区間 | カーネルの時刻の差 | クロック数の差 | 割った値 |
| --- | --- | --- | --- |
| 本番のコンソール → init | 0.970898 秒 | 約 4853 万 | 49.98 MHz |
| カーネルの時計が動き出す → init | 2.727118 秒 | 約 1 億 3640 万 | 50.02 MHz |

- どちらも 50 MHz になる。カーネルは、device tree に書いてあるタイマーの速さ (記録の `aclint-mtimer @ 500000Hz`。1 秒に 50 万回進むカウンタ) を信じて時刻を作る。
  割った値が 50 MHz なので、このカウンタはクロック 100 回で 1 進む勘定になり、カーネルにとって 1 クロックは 20 ns (ナノ秒) である
- つまり、カーネルの時刻は「50 MHz のボードで動いていたら何秒めか」を表す。PC の実時間とは関係が無い。
  カーネルの記録に `2.727134` とあっても、PC ではそこまで 417 秒かかっている
- カーネルの時刻の 0 は、クロック数の 0 ではない。時計が動き出すのが約 2420 万クロックめなので、0.48 秒ぶんずれる。
  表の右端の列 (クロック数 ÷ 50 MHz) からカーネルの時刻を引くと、どの行も約 0.48 秒になる

## CPU は働いているか、待っているか

`@@PC` の行の `retired` と、`@@IRQ` の行の SD カードの割り込みの数を、クロック数を横軸にして並べる。

```graph
# グラフ (tommie-fence の graph フェンス)
title: 図1 起動の進み — 終えた命令の数と SD カードの割り込みの数 (1000 万クロックごと)
x: クロック 百万 0..340
y:
  - 退役した命令 百万 0..140
  - SD の割り込み 回 0..400
data: 03-boot-progress.csv 模型の記録
notes:
  - band 160 290
  - text 165 125百万: init が SD カードを読む間 (命令がほとんど進まない)
  - mark 160
  - mark 290
```

![グラフ](https://tommie-jp.github.io/tommie-circuit-workbook/06-fpga/13-linux/graph/03-read-boot-log.svg)

図の点は、13-2 の起動 1 回の記録の値 (模型が数えた物で、実機で測った値ではない)。

| 区間 (クロック) | 退役した命令 | 1 命令あたりのクロック | SD の割り込み | していること |
| --- | --- | --- | --- | --- |
| 0〜1.6 億 | 9555 万 | 1.7 | 0 → 14 | OpenSBI とカーネルの初期化。CPU は働き続けている |
| 1.6 億〜2.9 億 | 1183 万 | 11.0 | 14 → 347 | init が SD カードから読む。CPU はほとんど待っている |
| 2.9 億〜3.34 億 | 2174 万 | 2.0 | 347 → 378 | シェルが起きて、名乗りとプロンプトを出す |

- 傾きが、CPU の忙しさである。最初の 1.6 億クロックは、1.7 クロックに 1 命令のほぼ一定の速さで進む。字の出ない区間でも同じ傾きなので、止まってはいない
- 1.6 億クロックめ (init が起きた所) で傾きが寝る。同時に SD の割り込みが増え始め、1000 万クロックに 20〜40 回ずつ、2.9 億クロックめまで続く。
  この間の `@@PC` の番地は、13 回のうち 11 回が同じ `ffffffff805d3ab0` で、13-1 で何も打たない間に見えた番地と同じである。
  CPU は割り込みを待って寝ていて、SD カードの読みが 1 回済むたびに少し進んでは、また寝る
- この「寝て待つ」区間が、起動のクロック数の約 4 割 (1.3 億 ÷ 3.34 億)、実時間で約 5 分半を占める。なぜ読み 1 回にこれほど待つのかは 13-12 で調べる
- 2.9 億クロックめの番地は `000000000012e47e`。初めてユーザーの番地が見える。BusyBox のシェルが動き出した所である
- カーネルの時刻 0.52 秒から 1.76 秒までの間 (約 5030 万〜1 億 1210 万クロック、実時間で 163 秒) は、字が 1 行も出ない。
  図ではこの間も傾きが変わらず、CPU は働いている。何をしているかは、この題では確かめていない

### 2 回走らせると同じ数になる

SD カード無しの `make linux` の記録と比べると、0〜1.3 億クロックの 14 個の `@@PC` の行は、番地も退役した命令の数も 1 字も違わない。
1.4 億クロックめから違う (SD カードがあるかないかで、カーネルの進む道が分かれる)。

- 模型には乱数も実時間も入らない。同じ像を同じ模型で回せば、何度やっても同じクロックに同じ事が起きる
- 止まったクロック (334 348 446) も、2026-10-30 に同じ模型で起動して保存した時 (13-6) と同じだった。
  13-1 のページが読み戻す時点 3 億 3432 万 8446 クロックめは、ここから 2 万を引いた数である
- この性質のおかげで、PC で保存した状態をブラウザで読み戻して続きを回せる (13-6・13-8)。また、うまく動かない所を、クロック数で名指しできる

## 最後のまとめを読む

```text
 ORC.B retired (Zbb string functions of Linux) : 73641
 cbo.zero retired (Zicboz, clear_page of Linux) : 61760
 clmul* retired (Zbc, the CRCs of Linux)        : 409908
 CSR instructions on stimecmp (Sstc)         : 1226
 LINUX RUN ENDED : the shell prompt
 334348446 cycles, 129116476 retired, 6156 traps, pc of the last retired ffffffff803ea3a4
 stop_code=1, cycle 334348446, 334348446 cycles in 857.7 s, 389826 cycles/s
```

- 最初の 4 行は、RV64GC に足した拡張の命令を、カーネルが実際に何回使ったかの数。たとえば `cbo.zero` はページを 0 で埋める命令で、6 万回使われている。
  CPU がこの拡張を持つと device tree で名乗っているので、カーネルが使う (13-1 の `/proc/cpuinfo` の `zicboz` `zbb` `zbc` `sstc`)
- `traps` は、割り込みと例外で CPU が飛んだ回数。6156 回のうち、SD カードの割り込みが約 380 回 (3.3 億クロックめで 378 回)。残りの内訳 (タイマー・ページフォールト・システムコール) は、この記録からは分からない
- `stop_code=1` はプロンプトで止まった印。root 待ちなら 3 (`make linux`)
